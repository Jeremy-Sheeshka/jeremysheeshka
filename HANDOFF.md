### What this project is
Rhythm Reader / "Curriculum Otherwise" (ETEC 531) - a reimagined sight-reading studio. An Astro site whose interactive games live as static pages under `public/games/rhythm-reader/`:
- `index.html` - the communal **Rhythm Bank** dashboard: a tap-to-notate recorder (16th-note grid) plus two banks. **Cultural Rhythm Bank** = shared, cross-browser, stored in Firebase via the Netlify function `netlify/functions/rhythms.mjs`. **Local Rhythm Bank** = per-user but ALSO persisted to Firebase via `netlify/functions/rhythms_local.mjs` (despite the name "local", both banks save server-side; "local" means a separate private collection, not browser storage). ### The two Free-Play modes (one file, one engine)
`fp-onboard.js` is shared by both modes; the opening gate "Are you new to reading rhythms?" sets `guidedDiff`:
- **No (easy)** - runs the red-annotation control tour first, then a guided Listen-then-tap exercise, then free practice. Generator `randBarEasy`: beat-aligned quarters + halves + beamed eighth-pairs, quarter rests when a rest appears, half rests rare, NO sixteenth notes at all.
- **Yes (hard)** - skips the tour, straight to free practice. Generator `randBarHard` builds each beat from `PAT_HARD`, a weighted library, so sixteenths ONLY appear in the figures `1 e + a`, `1 e a`, `e + a`, `1 + a`, `1 a`, `1 e`, `1 e +`. Eighth rests are used in lieu of sixteenth rests wherever a figure allows; the only sixteenth rests are the unavoidable internal ones inside the syncopated figures (weighted low). This eliminates lone flagged sixteenths and stray sixteenth rests.
- **Bars** selector is limited to **2 or 4** in BOTH modes (`applyBarOptions` always writes those two options; `readBars` clamps 2..4).

### Notation renderer + the click-locked cursor (important constraint)
Our SVG renderer lays notes on a UNIFORM grid: `pos(o).x = LM + (local+0.5)*uSlot`, with **2 bars per row** (`ROWCAP=2`). Noteheads are full size (`hr=6`). The red playhead (`#ob-ph`) is positioned by `cursorX(v)` using the EXACT same `LM+(local+0.5)*uSlot` map, so it lands on each notehead the instant its metronome click sounds - no lag, no jump. The row-wrap is a soft opacity fade, not a teleport. **Do not add a per-barline note margin**: a margin wider than time forces the cursor to speed up at the barline (the visible "jump" we removed). Full heads + clear barlines + a perfectly linear cursor only coexist at 2-bars-per-row; if you ever need 4-per-row you must shrink heads or accept heads touching the barline - those are the only three options, pick deliberately.
- **Sixteenth beams** (`drawBeams`): primary beam spans first-stem to last-stem of each group; the secondary (16th) beam is drawn stem-to-stem between adjacent sixteenths, and every partial stub is capped to `min(0.4*slot, 0.45*gap-to-neighbor)` and to the barline, so a beam line can NEVER poke past an adjacent stem. Lone sixteenths (only inside the listed figures) keep their curved double-flags.
- **Counting aid**: `ta`=quarter, `ti`=eighth, `ti ka ti ka`=the four sixteenths; Numbers mode = `1 e + a` per bar (never 5-8). The aid and the line cursor are gated LIVE by the gear-panel checkboxes (`marksOn()`/`cursorOn()` read the actual checkbox state each frame).

### Audio + tap judging
All sound routes through a single `masterGain` so **Stop** can silence everything instantly (`silenceMaster` ramps gain to 0 + bumps `sweepGen` to kill the cursor loop). Tap input is armed synchronously at scheduling (not on a lagging timer) so beat-1 of bar-1 registers; an early-tap guard (`t < tapMusicStart-WIN`) stops count-in taps from scoring. The grey box press is silent; the 1-2-3-4 count-in is audible. Correct taps click (1500Hz); misses are silent (red X only). The grey box shows NO dashed border during tapping.

### Draw layer (the fix that kept breaking)
The Draw button toggles our OWN `<canvas id="ob-drawcanvas">` which is created INSIDE `#ob-guided` (the white panel that always has real size) at `z-index:50`, above the SVG and the grey box. The original page canvas `#draw-canvas` is hidden and its handler suppressed via a capture-phase `stopImmediatePropagation` on the Draw button. Color is fixed **red** (`#dc2626`); the palette UI is hidden. Two past bugs, now fixed, that made drawing "do nothing": (1) the canvas was sized from a zero-height container so it was 1px tall; now `sizeDrawCanvas()` falls back through clientWidth -> getBoundingClientRect -> `#ob-guided` rect -> viewport, and re-runs on first stroke if `width<2`. (2) coordinate mapping used one scale for both axes; now `evpos()` uses separate x/y scales. Drawings are wiped on every new exercise (`clearDrawCanvas()` in `startTap`/`doNextFree`). When Draw is OFF the canvas is `pointer-events:none` so the grey box starts exercises; when ON the canvas intercepts strokes.

## How to work in this repo (response / tooling contract)

These conventions are what every future session should follow; they exist because loose assumptions have repeatedly broken the build.

- **Environment**: EndeavourOS, `zsh`. Always start a terminal block with `setopt NO_BANG_HIST` (multi-line pastes otherwise corrupt on `!`/history expansion). Pasted multi-line Python must arrive intact - if the prompt ends on `heredoc>` the block did not close; re-paste or type the closing `PYEOF` on its own line.
- **Response style**: terse and code-first. No long prose explanations unless explicitly asked. Deliver copy-paste terminal blocks. Each edit block is a `python3 << 'PYEOF' ... PYEOF` that (a) reads the target file, (b) makes the change - either anchored string replacement with an exact-count guard, or a full-file rewrite for the overlay engine, (c) runs `node --check` on any JS, (d) prints `verify ...` boolean lines proving each requested change landed, (e) `sys.exit(1)` WITHOUT writing if any guard/check fails (so a bad run never half-applies). The `git add/commit/push` is a SEPARATE block run only after the verify lines are green.
- **Git**: never commit or push unless the user's flow includes the commit block; never touch git speculatively. Commit messages are descriptive one-liners.
- **Read before asserting**: when unsure of a file's structure, provenance, or a selector, run a READ-ONLY probe (print line numbers / markup / token hits) and decide from evidence - do not guess. State observable facts as facts and inferences as inferences.
- **Edit strategy**: for `fp-onboard.js` prefer FULL-FILE REWRITE over many fragile micro-anchors - the overlay engine changes as a unit and partial edits have caused truncation/syntax failures. For small, isolated HTML/CSS tweaks, anchored replacement with count guards is fine. Always keep an idempotency guard (sentinel / "already present" check) so re-running is safe.
- **Safety rails that must survive every edit**: the click-locked cursor math (`cursorX`/`pos` share one uniform map); the 2-bars-per-row layout; `masterGain`-based Stop; tap armed at scheduling with the early-tap guard; Draw canvas inside `#ob-guided` with dual-axis `evpos`; settings checkboxes read live; Bars clamped 2..4; the two third-party black boxes left untouched.
